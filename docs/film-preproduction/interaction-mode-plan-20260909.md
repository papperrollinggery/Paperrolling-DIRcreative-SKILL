# 前期协作方式确认改进计划（按用户授权直接实施）

目标：新故事或影视前期开始时，先确认用户希望怎样协作，避免完整 brief 或“导演组”被当作直接执行的选择。

1. 在既有入口、Studio 和聊天协议说明三种交互方式：讨论共创、直接执行、关键节点讨论。说明创意组和导演组的职责；组名与真实子代理分别处理。
2. 在既有路由增加同项目的 interaction 状态。未选择时先等待；明确选择后复用；讨论中的“继续”仍是讨论。模式可以切换，不能授予媒体或外发权限。
3. 将状态加入 compact snapshot，并让命令行能在新进程读回。旧状态缺失此字段不能推定同意直接执行。局部编辑、参考分析、既定资产执行及维护保持原范围。
4. 验证首次输入、明确偏好、组名、选择回复、续聊、切换、节点确认、跨项目隔离和媒体授权边界；运行项目验证与独立行为审查。

验收：首轮不抢写全套；讨论有具体判断和建议且等待反馈；直接执行不重复问；关键节点按约定等待；旧功能和资产授权不回归。用户后续扩大授权到合并、全局安装、发布；用户已明确本次开发不需要再次确认方案，直接完成实现、审查、安装验证与发布读回。

## 研究依据（2026-09-09 实际打开官方文档）

- [Lovable Plan mode](https://docs.lovable.dev/features/plan-mode)：探索不必立刻形成计划；有可实施方向时产生可编辑计划，批准后按该计划执行。采用“讨论可以只得到清晰认识，开始制作需绑定可审阅范围”。
- [Replit Plan vs. Build](https://docs.replit.com/learn/plan-vs-build-mode)：讨论、审阅计划、点击 Start building 后切换到构建。采用明确开始入口，普通追问不当作开工。
- [Cursor Plan Mode](https://cursor.com/docs/agent/plan-mode)：复杂任务可先研究与澄清，审阅后点击构建；明确的小修改可直接执行。采用局部工作的轻量例外。

- [Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)：按任务逐步读必要参考，机械操作用脚本，先从真实失败案例改进。
- [Anthropic DOCX Skill 源码](https://raw.githubusercontent.com/anthropics/skills/main/skills/docx/SKILL.md)：按创建/编辑/读取给直接路径，聚焦接口易错点，产物写出后渲染检查。
- [Anthropic PDF Skill 源码](https://raw.githubusercontent.com/anthropics/skills/main/skills/pdf/SKILL.md)：常见操作给可执行短示例，表单和高级功能再读专门文档。

以上是官方文档和实际 Skill 源码证据，没有登录产品做用户实验，也不将其“优秀程度”作排名。迁移到影视制作的是按需加载、清晰输入、产物检查原则；没有假定文档工具的速度等于影视生成速度。

## 用户看见的完整流程

1. 新项目前期：读懂创意、复用已知材料；若交互方式未明确，调用一次 Codex 原生询问框。按钮为“讨论共创（推荐）”“直接执行”“关键节点讨论”。简述创意组负责剧情/动机，导演组负责表演/风格/镜头，按任务共同参与；用户可改为只用一组，组名不自动启动子代理。
2. 讨论共创：回应用户想法，提出具体故事或视觉建议，围绕当前有价值的问题发展。回答问题、解释原因、补充事实、改一处内容均不强制弹框。只有互斥方向或约定节点需要取舍才弹。
3. 收束：核心创意、风格/观看感受和下一步产物足够明确时，主动总结已定与未定内容，列出这轮会制作什么；原生框问“按此开始制作 / 继续调整”。不必固定讨论轮数，不必强行走故事、剧本、分镜各审批一次。
4. 等待：同一待答问题不会重复创建。预选、取消、超时、裸“继续/可以”不是生产确认；明确按钮提交或同义自然语言绑定当前展示范围才有效。用户问“为什么这样”时先回答，保留原确认。
5. 执行：按确认范围推进。讨论模式的生产确认与直接执行的明确开场选择具有各自作用域，不再重复审批同一范围。图片、视频、外发权限独立；若缺少真实授权，仅在相应动作前确认。反馈或失败只影响相关部分。
6. 调整：可随时改模式。改创意不自动丢弃所有成果；只让受影响的内容过期。新项目或制作范围实质变化需重新匹配选择，旧确认不外溢。

“继续讨论”“确认故事，进入剧本”“确认剧本，进入分镜”“讨论完成，准备生产”“确认开始生产”是可选快捷说法，不是必须背的口令。自然语言含义明确即可；仅“继续”保留当前模式和阶段。

## 状态与实现边界

沿用 Fast/Studio/Delivery 和现有路由，新增项目级交互选择与待答节点；不新造生产路由。保存当前模式、作用域、讨论阶段、已展示制作范围、待答问题及对应版本。原生工具调用和真实用户提交分开，模型判断与 Skill 要求在问题标题注明（例如“DIRcreative · 协作方式”）。

已接入路由、制作选择器、资产准备、执行检查和安装重放的状态透传；原始媒体请求与当前交互事件分开。旧状态缺失时不推定 direct，明确执行委托与小修改保留原行为。发布验收以对应版本的最终检查为准。

## 执行及发布顺序

实际任务效率取证 → 研究与设计 → 修订草稿和调用链 → 正反例回归 → 新进程/隔离安装与独立自然语言行为验证 → 完整项目验证 → 独立审查 → 合并 → 正式发布与全局安装 → 当前版本/入口/行为读回。

必要验收场景：模糊创意、完整 brief 未选模式、明确直做、只点名导演组、按钮选择、讨论中的继续/追问、同节点不重复弹框、收束后修改、明确开始、范围改动使旧确认失效、跨项目隔离、局部编辑、生成/外发授权、源码/ADCO排除。

## 草稿独立审查后需要修正的边界

以下问题已在隔离内存场景复现，将在本次开发中直接修复；它们是发布前验收项。

| 情况 | 正确行为 |
| --- | --- |
| 用户说“我之前选过直接执行”或问“直接执行会不会跳过讨论” | 解释或识别历史语境，不修改本项目交互模式 |
| 用户说“这个标题你来定” | 仅处理标题，不变更全项目模式或解除待制作确认 |
| 用户说“先不确认开始生产” | 保留未确认状态，不执行 |
| 讨论中临时分析参考片，再回到故事 | 保留原项目讨论选择，不重复首轮菜单、不损坏续聊状态 |
| 用户补充“女主角要更主动一些” | 在当前讨论里给建议，不因短句被分到局部路由而丢掉模式 |
| 用户说“准备生产”但范围尚未整理 | 先整理具体产物；不能显示指向空范围的开始按钮 |
| 原生问题已显示，用户问“为什么这样安排” | 回答原因，原问题仍待答，不重复创建新问题 |
| 用户改了已展示的制作范围 | 更新范围及对应问题版本；旧按钮提交不得确认新范围 |

## 一段预期对话（设计示例，非已运行回执）

用户：我想做个老朋友重逢的短片，还没想清楚怎么拍。

助手：这个题材可以从两个人对过去的不同记忆展开。我们先选一下合作方式。
原生框“DIRcreative · 协作方式”：讨论共创 / 直接执行 / 关键节点讨论。

用户选择讨论共创后：助手提出有区别的剧情或风格建议。用户问“为什么要这样结尾”时直接解释；用户补充人物经历时把它融入故事。普通讨论没有固定弹框，也不要求每句话都带一个问题。

当方向足够明确：助手归纳已定故事、风格与时长，列出下一步实际产物。例如“按刚才确定的克制写实方向，先完成一页故事和30秒剧本；本轮不出图。”原生框“DIRcreative · 开始制作”：按此开始制作 / 继续调整。

用户选择开始：只执行列明的故事和剧本范围。用户选择调整：回到相关创作问题，保留已经确定的其他内容。用户只说“继续”或没有提交：不将它视作开工确认。

## 效率优化范围（用户追加）

结合指定任务的实际时间线，分别统计首个内容、首次实际生图调用、生成耗时、接口错误返工及可见交付；不能把累计 token 或规则数量当速度结论。优先使用现有模块和公开入口，修复真实接口障碍、无依赖资产前置被全片计划拖延、重复读取和未展示成果。保留身份/五视图/空间/真实图片质量检查，必要门禁在实际依赖边界执行。

本次开发无需再次弹框确认；此条只管本开发任务，不改变被开发产品对终端用户的交互契约。

## 由真实前向测试发现的输入修复

人物执行契约与 inventory/stress 描述不是同一种结构。公共输入说明现在提供正确的可填写结构，准备器在调用 provider 之前检查字段和事实绑定。执行检查复用相同字段验证，保留完整五视图、身份、材质及左右约束。词序和内容词仍须保留，允许标点、连字符与连接词 and 的排版差异；这属于文字保真检查，不冒充语义或视觉审核。

独立资产按真实依赖组织批次。结构文件的生成、接口校验及故障提示不再由每次生产临时编程；准备出的真实调用参数直接交给对应媒体工具。产物展示与质量采纳分别处理，发布后的效率结论仍需实际任务时间证据。

## 制作、修复与交付的状态边界

公共preparer已连接现有局部修复方法，`--repair-changes`只消费已记录缺陷和实际源图，使用相同input lock/handoff/packet；`--best-base-plan`必须与修复一起使用。旧create包不能被误当作局部编辑。

制作中的未审批候选可以暂缓画幅缺陷以进入修复；文件、哈希、身份、结构和已审批资产仍严格检查。完整交付继续使用严格validate_plan，不以准备ready或repair结果代替用户验收。实际前向试验产生了原图并完成一次局部方向修复，私人日志及媒体不进入发布包；不把单张回放耗时解释为整片提速比例。
